# ひとこと・改善案

## 仕様

- 右上の「管理メニュー（⋮）」内の「ひとこと送る」から開く公開コメント欄。読み取りはログイン不要、投稿・通報・本人削除は既存のGoogleログインを利用。
- 本文500文字、公開ニックネームは任意16文字（空欄は「学習者」）。Authの名前・メール・UIDは公開レスポンスに含めない。購入・個人情報の相談は従来のメール窓口へ。
- 運営は返信（1000文字）を履歴に追記でき、投稿者本人も追加コメント（500文字）で返事ができる。第三者の返信・いいね・プッシュ通知は含めない。返信は公開で、運営／投稿者の区別はサーバーで決める。
- 対応状況は「受付済み」（初期値）・「確認中」・「対応予定」・「対応済み」。運営だけが変更でき、変更も日時付きで履歴へ残す。「受付済み」は運営による既読を意味しない。
- 返信・追加コメント・対応状況の変更を合わせ、1投稿40件まで。上限時は古い履歴を切り捨てず追記を止める。投稿削除はそのやりとり全体を削除する。個別返信の編集／削除は未対応で、個人情報等の問題は投稿単位の非公開化・削除で対応する。
- 一覧は直近100件から公開分の最大50件。大量運用前にページングと通報一覧の独立画面を検討する。更新ボタン／再度開く操作で返信を確認する。
- 全投稿はプレーンテキスト。本文をHTMLとして挿入しない。公開注意書きを表示する。
- 新規投稿は60秒間隔、投稿者の追加コメントは30秒間隔、両者合計でUTC日付の1日10件。その他の書き込みは3秒間隔。Firestoreトランザクションで追記・上限を検証。同一アカウントの同一投稿への通報は重複カウントしない。
- 追加返信の下書きは画面を更新してもメモリ内に保持し、送信成功時に消す。認証変更／ページ再読み込み時は破棄。運営返信は既存の返信を入力欄へ入れず、空欄から追記する。
- `feedback_limits/{uid}.blocked = true` でその利用者の書き込みを停止可能。通報は運営が確認し、件数だけで自動削除しない。

## NOTEでの参考事例（ユーザー提供画像）

- スマホ版で復習をランダムにしたいという質問に、運営が謝意と追加予定を返信。その後に実装完了を報告し、利用者から対応の早さへの驚きと感謝が返っている。
- 参考にする価値は、短い言葉で要望を送れることと「受け付けた→対応した→利用者が確認した」という流れが第三者にも見えること。画像の相対時刻から正確な対応時間や日付は断定しない。
- この事例を参考に返信履歴・対応状況・投稿者の追加コメントを実装した。既存の単一返信は読取時に履歴として扱い、次の追記時に元の返信とともに保存する。日時不明の旧返信に日付を作らない。
- 本事例は設計・文面の参考用。投稿者名を含む実コメントのアプリ内転載や本人投稿としての登録は行わない。表示例に使う場合は要約し「NOTEで寄せられた声（紹介）」等と出典・性質を明示する。

## 構成・権限

- UI：`js/feedback.js`、`feedback.css`、`index.html`。共通モーダル管理へ登録済み。
- API：`functions/feedback.js`、公開関数名 `feedback`（us-central1）。クライアントからFirestoreへ直接アクセスさせない。
- `feedback_posts` に本文・`thread`配列・対応状況と非公開の所有者UIDを保存。履歴は1ドキュメントへのトランザクション追記で競合を保護する。旧UIとの互換用に`reply/repliedAt`へ最新の運営返信も残す。`feedback_reports` と `feedback_limits` もクライアント直接アクセス禁止。
- 運営認証はFirebase Authのカスタムクレーム **`feedbackAdmin: true`** のみ。メール文字列やクライアントの申告では許可しない。
- 権限付与はユーザー指定アカウントのUIDを確認し、信頼できるAdmin SDK環境で既存customClaimsを保持して追加する。2026-09-05に指定されたGoogleアカウントへ付与済み。Admin SDKで再読取し、`feedbackAdmin: true` と既存権限の保持を検証した。付与後は再ログイン等でIDトークンを更新する。アカウントのメール・UIDはこの公開リポジトリに記載しない。

## 公開前

1. 運営にするアカウントのUIDを確認し、上記クレームを設定する。
2. `node --test functions/feedback.test.js`、`node node_modules/playwright/cli.js test tests/feedback.spec.js`、`npm run test:mobile-modals` を実行する。
3. デプロイを依頼された場合のみ `npx firebase deploy --only functions:feedback,firestore:rules --project tenioha-game` を実行。UIは既存のGitHub Pages公開手順に従う。
4. 公開後、一般利用者と運営の別アカウントで投稿→返信→再閲覧、削除・通報を確認する（実投稿を伴うため明示したテスト投稿を使用）。

API未デプロイ時は接続エラーになる。架空の投稿や送信成功を本番UIに表示するフォールバックは設けない。E2EではAPIをモックし、本番への投稿を行わない。

2026-09-05：Functions全8関数とFirestoreルールのデプロイ完了。公開APIの一覧取得200・CORS応答204・未ログイン投稿拒否401を確認した。UIは `2026.0905.2022` の公開対象。実ユーザーとしての投稿・返信の往復は未確認であり、公開後に運営アカウントで再ログインして確認する。
