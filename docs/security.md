- Functionsの間接依存だけを互換範囲で更新。Firebase Admin 13系・Functions 7系・Stripe 20系、Node 24を維持する。メジャー移行や `audit fix --force` は行わない。

- Functions本番依存の既知警告は3件→0件。警告の成立には利用方法・設定条件があり、本アプリでの悪用や侵害を確認したわけではない。特にgRPCはFirestoreのクライアント用途で、当該サーバー認証設定の使用は確認していない。
- `functions/request-security.js`：購入画面生成とアプリ内コード適用を、認証済み利用者ごと・各操作ごとに60秒5回へ制限。6回目はHTTP429とRetry-After。コード失敗も数え、対象コードの照会・Stripeへの要求より前に止める。ランキング閲覧・通常学習・スコア送信には適用しない。
- 制限はFirestoreトランザクションで複数インスタンス間でも共有する。`sensitive_action_limits/{操作}-{UIDのSHA256}` を1利用者・1操作につき1個再利用し、IP・トークン・コード・メールを保存しない。時間窓経過時に上書きする。無制限のリクエスト履歴は作らず、TTL設定は追加していない。既存のデフォルト拒否ルールでクライアント直接アクセスは禁止される。
- 制限の読取失敗は迂回せずエラーにし、購入画面生成・コード付与を実行しない。コードの不正なパス文字も付与前に拒否。既存の固定Price、入金後のWebhook付与、コードの期限加算・利用済み判定は維持する。
- `.gitignore`：各階層の `.env`／`.env.*`、標準的なAdmin SDK鍵ファイルを除外し、`.env.example` は残す。過去のコミットや追跡済みファイルから秘密を消す機能ではない。

## 非公開停止情報・App Checkの準備（2026-10-22、未公開）

### 実装

- `firestore.rules` の停止対象リテラルを除き、`security_private/blocklist`（schemaVersion 1、blockedUids／blockedEmailsの配列）を参照する。文書の直接読取・書込はクライアント全面拒否。本人の学習保存・サブコレクションだけ許可し、購入フィールドの保護は維持する。設定欠落・フィールド型不正では許可せず停止する。
- `functions/account-security.js` で同じ文書を参照する。認証後の購入・コード適用・復習送信・プロフィール・ゲスト引継ぎ・認証付き順位・投稿に適用。読み込みは1.5秒上限、同時取得をまとめ、最大30秒キャッシュする。期限後の通信障害を古いキャッシュで迂回しない。匿名の公開一覧は継続する。Stripeの署名付きWebhookは対象外とし、停止設定の障害でも入金済み購入の付与を失敗させない。
- `functions/app-check-security.js` はHTTP APIの `X-Firebase-AppCheck` をAdmin SDKで検証し、対象アプリIDも照合する。初期モードはobserveで旧版を遮断しない。off／observe／enforceを区別し、設定ミスは503。検証は2.5秒上限、秘密値・UID・メールをログに出さず、状態ごとに最大1分1回の観察ログだけ出す（全件数の統計ではない）。OPTIONSとStripe Webhookを保護対象から除外する。
- `js/app_check_client.js` をHTML・版更新・キャッシュへ登録。既存と同じFirebase SDK 10.7.1でEnterprise providerと自動更新を準備し、Functions・購入・コード適用・投稿へヘッダーを付ける。サイトキーは未設定のため現在はSDKを追加取得せず、localhostも無効。設定後の初期化・ヘッダー取得は各1秒で打ち切り、アプリを無期限に止めない。URLや独自の端末保存へトークンを入れない。
- App Check・権限・回数制限等の403／429／503で復習の未送信イベントを捨てない。入力不正の400／422だけを従来どおり破棄し、同じeventIdで再送できる。購入APIの401／403／429／503は外部Payment Linkへ自動迂回せず、短いエラーを表示する。通常の購入・署名検証・入金後の付与は維持する。

### 移行・公開手順（明示的な承認後のみ）

1. 分離した公開用checkoutへ今回の差分だけを取り込む。`node scripts/security-config.cjs --dry-run` は既存CLI認証でデプロイ済みルールと非公開文書だけを読み、対象件数・準備状態を表示する。実値・トークン・管理API本文は出力・ファイル保存しない。
2. 承認された場合だけ同スクリプトの `--apply` を実行する。現行ルールの停止情報をメモリー上で取り込み、既存の停止情報を集合和で保持して作成／更新する。新規作成条件またはupdateTimeの事前条件で上書き競合を防ぎ、再読取で包含を確認する。形式不明・既存文書不正は勝手に空設定へ置き換えない。
3. `npm run security:check` が成功することを確認する。既存の停止がすべて含まれていない・認証不在・読取失敗・別プロジェクトなら失敗する。Functions／Firestoreのpredeployにも同じチェックを登録済みで、未移行での公開を止める。通常のFirebase CLI以外からの直接公開やGitHubへのpushまでは制御しない。
4. 新ルールとFunctionsを公開する。依存修正は全Functionsへ反映する。先に非公開文書を作るため、ルール／APIのどちらから更新しても空設定で解除・締出しにならない。旧ルールに戻す場合も非公開文書は消さない。Git履歴の個人情報消去には別の履歴整理・承認が必要。
5. App Checkは別段階。FirebaseでWebアプリにreCAPTCHA Enterpriseのサイトキー・許可ドメインを登録し、クライアントのSITE_KEYへ設定する（公開キー）。observeのまま更新し、実機Safari・PWA・旧版・通信制限で実トークンを確認する。十分に確認するまでenforceやFirestore側の強制適用をしない。Stripeの鍵や入金条件は変更しない。
